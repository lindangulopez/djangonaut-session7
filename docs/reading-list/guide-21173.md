### 1. Deleting the parent, for each `on_delete` option

The pull request says: "`ForeignObject.on_delete`: Behaves the same as `ForeignKey.on_delete`."

| `on_delete` | What happens when the parent is deleted | Same as `ForeignKey`? |
| --- | --- | --- |
| `CASCADE` | The child is deleted | Yes |
| `PROTECT` | `ProtectedError`, nothing deleted | Yes |
| `RESTRICT` | `RestrictedError`, nothing deleted | Yes |
| `DO_NOTHING` | The child stays, still pointing at the deleted parent | Partly: with a `ForeignKey`, the database's constraint would normally refuse the orphan (not tested here) |
| `SET_NULL` | `FieldError: Cannot update model field <ForeignObject: p> (only concrete fields are permitted)` | **No** |
| `SET_DEFAULT` | The same `FieldError` | **No** |
| `SET(0)` | The same `FieldError` | **No** |
| `DB_CASCADE` | The child stays | **No**, nothing happens |
| `DB_SET_NULL` | The child stays, `(pa, pb)` still `(1, 2)` | **No**, nothing happens |
| `DB_SET_DEFAULT` | The child stays, `(pa, pb)` still `(1, 2)` | **No**, nothing happens |

Two different causes. (i) The `SET_*` options ask the ORM to update the `ForeignObject` field to `NULL` or a default. A `ForeignObject` has no column of its own, so the update is refused (`add_update_values` in `django/db/models/sql/subqueries.py`). The columns that would have to change are `pa` and `pb`. (ii) The `DB_*` options, new in Django 6.1, leave the work to the database's `ON DELETE` clause. The collector skips them (`SKIP_COLLECTION` in `django/db/models/deletion.py`), and a `ForeignObject` creates no foreign key constraint, so nobody does the work.

### 2. System checks for `on_delete`

| Model | Check result |
| --- | --- |
| `ForeignKey`, `SET_NULL`, field not nullable | `fields.E320` |
| `ForeignObject`, `SET_NULL`, fields not nullable | No error |

The `on_delete` checks (`fields.E320` to `fields.E324`) are in `ForeignKey._check_on_delete`, in `django/db/models/fields/related.py`. `ForeignObject` does not run them, so the mistakes in table 1 pass `check` silently.

### 3. `models.E049`, under `from_fields`

The pull request says: "When `from_fields` contains more than one entry, **it** cannot appear in `indexes`, `constraints`, or `unique_together`. Doing so raises `models.E049`."

| What is named in `Meta` | Check result |
| --- | --- |
| `Index(fields=["p"])`, the `ForeignObject` itself | `models.E049` |
| `unique_together = [("p", "pa")]` | `models.E049` |
| `Index(fields=["pa", "pb"])`, the fields listed in `from_fields` | No error |

So "it" is the `ForeignObject` field, not `from_fields`. The fields in `from_fields` can be indexed.

### 4. `to_fields` checks

The pull request says the target columns must be unique, "Otherwise the system check framework raises `fields.E310`, `fields.E311`, or `fields.E312`."

| Target model | Check result |
| --- | --- |
| No uniqueness on `(a, b)` | `fields.E310` |
| `UniqueConstraint` on `(a, b)` with a `condition` | `fields.E310` |
| `UniqueConstraint` on `(a, b)` without a condition | No error |
| `to_fields` names a field that does not exist on the target | `fields.E312` |

So `fields.E312` is not about uniqueness, and a conditional `UniqueConstraint` does not count.
